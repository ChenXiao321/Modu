# Product Brief: Modu

## Executive Summary

Modu 是一款面向汽车电子行业的 AI 驱动软件模块开发平台。当前，汽车电子工程师在开发汽车电子软件模块时，面临开发效率低、文档质量参差不齐、测试能力不足以及覆盖率难以达标等系统性痛点。Modu 通过一条端到端的智能流水线，将需求分析、方案设计、代码构建、测试用例生成、静态测试、动态测试执行到发布全过程自动化，并原生满足 ASPICE、ISO 26262 功能安全及 ISO 21434 网络安全等汽车行业严苛的过程合规要求。所有产出内置双向追溯链接，可直接对接 Siemens Polarion ALM 系统。我们的目标是让资深工程师更高效，让萌新工程师也能产出符合车规标准的高质量软件模块。

## The Problem

在汽车电子领域，软件模块（如 TLF35584 电源管理芯片驱动）的开发是整车软件栈中高频且高风险的环节。开发团队当前面临三大核心痛点：

1. **效率瓶颈**：从分析上游输入文档到产出可交付的模块代码、设计文档和测试用例，大量工作依赖人工重复劳动，周期冗长。
2. **质量不稳定**：文档编写高度依赖个人习惯，输出物质量参差不齐，难以满足 ASPICE 过程要求；测试能力受限于团队经验，测试覆盖率往往不足。
3. **合规门槛高**：功能安全（ISO 26262）和网络安全（ISO 21434）对开发过程有严格的追溯性和验证要求，人工执行不仅成本高，而且容易遗漏。

现有方案要么是芯片厂商提供的专用配置工具（如 STM32CubeMX），仅覆盖单点且局限于主芯片；要么是通用的 AI 编程助手，缺乏对汽车电子合规流程的深度理解，无法输出满足车规要求的完整产物。

## The Solution

Modu 提供一个覆盖全生命周期的智能开发流水线，通过 Web 界面进行统一交互。用户只需在 Web 界面上传上游输入文档——无论是需求规格、架构设计、接口说明，还是芯片手册（支持 PDF、Word、Excel、图片、TXT、PPT 等常见格式），即可依次完成：

- **需求分析**：自动提取并结构化需求与功能定义
- **方案设计**：基于需求生成符合 ASPICE 要求的设计文档与实现方案
- **代码构建**：输出高质量、可编译的模块代码
- **测试用例生成**：基于需求和设计自动生成测试用例（含边界条件、等价类、故障注入场景）
- **静态测试**：
  - MISRA C/C++ 规则合规检查
  - 代码复杂度与圈复杂度分析
  - 代码规范与风格一致性扫描
- **动态测试执行**：
  - 基于需求与设计自动构建 Mock/Stub 环境并执行单元测试
  - 接口/API 一致性验证
  - 资源使用监控（内存、堆栈、CPU 占用）
  - 故障注入测试（Fault Injection）
  - 回归测试（模块迭代时自动重跑全量用例）
  - 代码覆盖率分析（语句覆盖、分支覆盖、MC/DC）
  - **网络安全测试**：依据 ISO 21434 要求进行渗透测试、攻击面分析与安全需求验证
- **发布**：打包符合组织标准的交付物

每个阶段完成后均触发设计校验节点，并保留人工确认环节，确保 AI 加速的同时不牺牲可控性与问责链。所有产出物内置双向追溯链接，可直接导入 Siemens Polarion ALM 系统形成完整的追溯矩阵。

## What Makes This Different

- **端到端闭环**：市面工具多聚焦代码生成或测试单点，Modu 是唯一覆盖"需求→文档→代码→测试→发布"全链路且原生合规的平台。
- **合规原生**：不是事后补文档，而是将 ASPICE、ISO 26262、ISO 21434 的要求内建到每个活动步骤中，自动产生追溯链。
- **降低门槛**：平台化、向导式体验，使初级工程师也能在汽车电子领域快速产出符合标准的成果。
- **汽车电子软件模块垂直聚焦**：区别于面向通用 MCU 主芯片的工具，Modu 专注于汽车电子软件模块这一高价值、高复杂度的细分领域。

## Who This Serves

**主要用户**：汽车电子 OEM 及 Tier-1 供应商的嵌入式软件开发团队，尤其是负责 BMS、车身电子、底盘系统中各类软件模块开发的工程师。

**关键用户画像**：
- **资深工程师**：希望从重复性文档和样板代码中解放出来，将精力集中在架构和复杂逻辑上
- **萌新工程师**：需要平台引导完成符合车规标准的开发，降低学习曲线和犯错成本

**购买者**：通常是研发总监、软件质量负责人或工具链采购部门，他们关注合规通过率、交付周期和人力成本。

## Success Criteria

- **开发效率**：软件模块从需求到发布的平均周期缩短 40% 以上
- **文档质量**：设计文档首次评审通过率从当前的不足 60% 提升至 90% 以上
- **测试覆盖**：动态测试代码覆盖率达到对应 ASIL 等级的目标要求，静态测试零高危告警
- **合规达成**：通过第三方 ASPICE 及功能安全审核时，过程资产一次性通过率 95% 以上
- **用户采用**：目标客户在试点项目中，80% 以上工程师可在无培训情况下完成首个模块开发

## Scope

**MVP 范围内**：
- 支持主流汽车电子软件模块（含外设驱动、通信协议栈、传感器抽象层等）的开发；平台为开放系统，不绑定特定芯片型号，通过 AI 解析用户上传的上游文档（需求、架构、接口、芯片手册等）自动生成模块代码
- MVP 阶段目标平台锁定为 **Infineon AURIX TC38x**，编译器为 **Tasking 6.3.1**；用户需提供基础工程（Base Project），Modu 生成的模块代码集成到该工程中完成编译与测试
- 覆盖需求分析、方案设计、代码生成、测试用例生成、全栈测试执行及发布环节
  - 静态测试：MISRA C/C++ 合规检查、代码复杂度分析、代码规范扫描
  - 测试用例生成：基于需求与设计的边界条件/等价类用例生成、故障注入场景生成
  - 动态测试执行：Mock/Stub 环境构建与单元测试执行、接口一致性验证、资源使用监控（内存/堆栈/CPU）、回归测试、覆盖率分析（语句/分支/MC/DC）
  - 网络安全测试：依据 ISO 21434 的渗透测试、攻击面分析与安全需求验证
- 内建 ASPICE Level 2 过程要求及 ISO 26262 功能安全实践；根据模块的实际 ASIL 等级（A/B/C/D）自动匹配合规流程、测试覆盖率及验证深度
- 代码生成与测试运行环境适配 TC38x AUTOSAR Classic 架构（Modu 生成 CDD 复杂设备驱动模块）
- 平台内置代码生成模板与规范，约束 AI 输出代码的文件结构、命名风格、接口模式及编译器适配格式，确保生成代码可直接集成到用户基础工程
- 提供基于 Web 的统一操作界面，支持需求上传、流程跟踪、产物查看与评审
- 提供设计校验和人工确认机制，支持结构化评审记录（签名、时间戳、评审意见）
- 所有产出物内置双向追溯链接，可直接对接 Siemens Polarion ALM 系统

**明确排除**：
- 主芯片（MCU/SoC）底层启动代码及操作系统移植（由用户提供基础工程覆盖）
- IDE 插件（如 VS Code / Eclipse）集成（后续版本扩展）
- 与第三方工具链（如 Vector、EB tresos）的实时集成（保留接口，但不保证即插即用）
- 硬件在环（HIL）系统级测试
- ISO 26262 工具认证（TCL 评估）流程（后续迭代扩展）
- ASIL-D 最高功能安全等级的全套认证证据包（形式化验证报告、独立安全评估等）的自动生成与输出（平台支持按 ASIL-D 标准开发模块，认证证据包后续迭代扩展）

## Vision

Modu 的短期目标是成为汽车电子软件模块开发领域的标杆工具，帮助客户以更低的成本和更短的时间产出合规、高质量的软件模块。中期来看，平台将扩展至更广泛的中间件及复杂协议栈开发，覆盖 ASIL-D 等高等级功能安全场景，并探索辅助生成功能安全分析（FMEA/FTA）的能力。长期愿景是成为汽车软件工程领域的"智能副驾驶"，让每一个汽车电子模块的开发都具备可追溯、可验证、可复现的工业化水准。同时，平台将探索与芯片厂商的合作模式，反向为半导体厂商提供 SDK 生成与验证服务，形成 B2B2B 生态闭环。
