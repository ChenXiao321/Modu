# Modu - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for Modu, decomposing the requirements from the PRD, Architecture requirements into implementable stories.

## Requirements Inventory

### Functional Requirements

FR1: 工程师可以上传上游输入文档（需求规格、架构设计、接口说明、芯片手册等），支持 PDF、Word、Excel、图片、TXT、PPT 格式，单文件最大 100MB。
FR2: 平台可以自动解析上传文档并提取结构化功能需求与寄存器定义。
FR3: 平台可以识别并单独标注安全关键参数（时序、电压阈值、温度范围、看门狗周期、超时时间等），将其注册为独立可追溯需求条目。
FR4: 平台可以对扫描件或图片格式文档的 OCR 提取结果输出置信度评分。
FR5: 平台可以基于解析后的结构化需求生成符合 ASPICE Level 2 要求的设计文档。
FR6: 工程师可以在 Web 界面逐节审查设计文档，对任意章节进行在线修正或添加评审意见。
FR7: 平台可以在每个设计校验节点记录结构化评审记录，包含签名、时间戳和评审意见。
FR8: 平台可以基于已批准的设计文档生成符合 MISRA C/C++ 规范的 C 语言模块代码。
FR9: 生成代码必须内嵌 Polarion 需求追溯 ID，实现需求到代码的双向追溯。
FR10: 生成代码应符合平台内置代码生成模板的文件结构、命名风格、接口模式及编译器适配格式。
FR11: 平台可以根据模块声明的 ASIL 等级（A/B/C/D）自动调整代码生成策略和验证深度。
FR12: 平台可以基于需求和设计文档自动生成测试用例。
FR13: 测试用例必须覆盖边界条件、等价类划分和故障注入场景。
FR14: 平台可以执行 MISRA C/C++ 合规检查并生成合规报告。
FR15: 平台可以执行代码复杂度和圈复杂度分析。
FR16: 平台可以执行代码规范与风格一致性扫描。
FR17: 平台可以自动构建 Mock/Stub 环境并执行单元测试。
FR18: 平台可以执行接口/API 一致性验证。
FR19: 平台可以监控并记录动态测试期间的资源使用（内存、堆栈、CPU 占用）。
FR20: 平台可以执行回归测试，在模块迭代时自动重跑全量历史用例。
FR21: 平台可以生成代码覆盖率报告（语句覆盖、分支覆盖、MC/DC）。
FR22: 平台可以执行安全代码审查，检测生成代码中的安全漏洞。
FR23: 平台可以基于模块接口设计执行攻击面分析。
FR24: 平台可以验证 ISO 21434 基线安全需求的覆盖率。
FR25: 平台可以将所有产出物（设计文档、源代码、测试用例、测试报告、评审记录、追溯矩阵）打包为符合组织标准的交付物。
FR26: 所有产出物必须内置双向追溯链接，实现需求↔设计↔代码↔测试的完整追溯链。
FR27: 平台可以将代码产物（源文件、头文件）提交至 Git 仓库，并将文档/测试用例/报告提交至 Siemens Polarion ALM 系统。
FR28: 平台管理员可以配置 Siemens Polarion ALM 的连接参数和导入映射规则。
FR29: 平台管理员可以配置与客户现有 AD/LDAP 认证系统的集成。
FR30: 平台管理员可以创建租户隔离空间，为不同团队配置独立的代码模板和合规策略。
FR31: 平台管理员可以监控平台运行状态并接收告警通知。

### NonFunctional Requirements

NFR1 (PERF-001): 系统应保证页面首次加载时间 ≤ 3 秒（95th percentile），测量方法为首屏内容渲染完成（FCP），上下文为内网环境（带宽 ≥ 100Mbps，延迟 ≤ 5ms）。
NFR2 (PERF-002): 系统应保证文档上传（< 50MB）完成时间 ≤ 10 秒，测量方法为客户机发送完最后一个字节到服务器返回确认的时间，上下文为内网环境、PDF/Word 格式。
NFR3 (PERF-003): 系统应保证 AI 需求分析（单文档，≤ 50 页）完成时间 ≤ 60 秒，测量方法为从用户点击"开始分析"到解析结果呈现的时间，上下文为文档以标准排版格式存储、AI API 正常响应。
NFR4 (PERF-004): 系统应保证代码生成（单模块，含方案设计 + 代码 + 测试用例）完成时间 ≤ 90 秒，测量方法为从用户确认设计到所有产物生成完毕的时间，上下文为 ASIL-B 等级模块、标准 CDD 复杂度。
NFR5 (PERF-005): 系统应保证静态测试执行完成时间 ≤ 30 秒，测量方法为从代码提交静态扫描到报告生成的时间，上下文为单模块代码量 ≤ 5000 行。
NFR6 (PERF-006): 系统应保证动态测试执行（含编译 + Mock 构建 + 单元测试运行）完成时间 ≤ 5 分钟，测量方法为从测试触发到覆盖率报告生成的时间，上下文为 Tasking 6.3.1 编译器、TC38x 模拟目标环境。
NFR7 (PERF-007): 系统应保证全流程执行（从需求上传到发布打包）完成时间 ≤ 10 分钟，测量方法为平台自动执行阶段的累计时间（不含人工审查等待时间），上下文为标准复杂度 CDD 模块、无队列阻塞。
NFR8 (REL-001): 系统在私有化部署环境中的可用性应 ≥ 99.5%，测量方法为月度正常运行时间 / 总时间，上下文为单实例部署、计划内维护窗口除外。
NFR9 (REL-002): 系统应在流水线执行过程中遭遇网络中断时支持任务重试或断点续传，测量方法为模拟网络中断 30 秒后恢复，验证任务状态一致性和产物完整性，上下文为 AI API 调用阶段或文档解析阶段。
NFR10 (REL-003): 系统应保证表单输入（如人工评审意见）在意外刷新或浏览器崩溃后不丢失，测量方法为输入后 5 秒内强制刷新页面，验证数据恢复完整性，上下文为所有包含文本输入的 Web 表单。
NFR11 (SEC-001): 系统应保证所有客户端与服务端通信通过 HTTPS/TLS 1.2 或更高版本加密，测量方法为网络抓包验证无明文传输，上下文为内网及跨网段访问场景。
NFR12 (SEC-002): 系统应保证敏感文档原文不在前端浏览器持久存储（LocalStorage / IndexedDB），仅缓存处理后结构化数据，测量方法为审查前端存储内容，确认不包含原始 PDF/Word 二进制片段，上下文为所有支持的浏览器。
NFR13 (SEC-003): 系统应保证 AI API 调用参数中不包含客户敏感信息（芯片型号、客户项目名称、内部架构细节），测量方法为审计网关日志，确认传出请求经过脱敏处理，上下文为所有第三方大模型 API 调用。
NFR14 (SEC-004): 系统应记录所有 AI API 调用的完整审计日志，包含用户标识、时间戳、请求摘要、响应状态、模型版本，测量方法为审计日志完整性校验，保留周期 ≥ 2 年，上下文为私有化部署环境中的审计网关。
NFR15 (MAINT-001): 系统应支持代码生成模板的版本化管理，允许管理员升级模板版本而不影响历史模块产物，测量方法为验证同一模块使用模板 v1 和 v2 生成产物可追溯且互不覆盖，上下文为模板更新发布流程。
NFR16 (MAINT-002): 系统应支持平台平滑升级，保证用户数据和配置无损迁移，测量方法为升级前后数据库 schema 兼容性验证和数据完整性校验，上下文为主版本号变更（如 1.x → 2.x）。
NFR17 (USAB-001): 系统应支持 Google Chrome、Microsoft Edge、Mozilla Firefox 的最新 2 个主版本完全兼容，测量方法为自动化 UI 测试覆盖核心用户旅程，上下文为桌面端浏览器。
NFR18 (USAB-002): 系统应保证在 1920×1080 分辨率下完全展示所有功能界面，在 1366×768 分辨率下核心功能可用，测量方法为视觉回归测试，上下文为工程师常用桌面显示器和笔记本电脑。
NFR19 (USAB-003): 系统应满足 WCAG 2.1 AA 级无障碍要求，测量方法为自动化无障碍扫描（如 axe-core）零 Critical 级别违规，上下文为所有公共页面和表单。
NFR20 (SCAL-001): 系统架构应支持将第三方大模型 API 切换为本地部署模型，切换过程不改变业务层接口，测量方法为验证 API 适配层接口稳定性（至少支持 2 种不同模型后端），上下文为未来本地 GPU 集群部署。
NFR21 (SCAL-002): Polarion 集成层应支持客户自定义 Work Item 类型、自定义字段和自定义链接角色，测量方法为配置界面验证至少 3 种不同客户的 Polarion 配置适配，上下文为不同 OEM/Tier-1 客户的 Polarion 实例。

### Additional Requirements

- 多租户数据隔离模型：PostgreSQL shared schema + tenant_id + Row-Level Security (RLS)
- 认证与授权策略：AD/LDAP 集成（标准 LDAP/LDAPS 协议）+ JWT（短时效 access token + 长时效 refresh token）+ RBAC（角色：Platform Admin, Tenant Admin, Engineer, Quality Auditor, Read-Only User）
- AI 服务部署拓扑：AI Worker 作为独立容器运行，通过内部 HTTP 网络与 backend 通信，防止 AI 推理消耗的资源影响主 API 服务稳定性
- 编译器/测试执行沙箱环境：Tasking 6.3.1 编译器和 TC38x 模拟器在隔离 Docker 容器或专用工作节点中执行
- 外部工具链集成架构：Polarion REST API adapter、GitPython/libgit2、python-ldap、LiteLLM unified LLM proxy
- 文件存储策略：本地 Docker Volume 为默认存储；MinIO 作为可选 S3-compatible 升级方案
- 监控告警方案：Prometheus + Grafana（MVP 可选）；邮件/企微/钉钉告警（FR-REQ-031 要求）
- Agent 架构：LangGraph 作为 Agent 编排框架，7 个 Agent（DocumentParserAgent, DesignAgent, ReviewGate, CodeAgent, TestAgent, SecurityAgent, ReleaseAgent）
- 检查清单执行模型：程序化执行（YAML 定义，Python 执行），确保确定性合规验证
- 模板版本化管理：JSONB 列存储模板，含 version、effective_from、effective_to 字段
- 审计日志保留周期：评审记录 ≥ 7 年；AI API 调用审计 ≥ 2 年
- 工作流引擎设计：YAML 定义工作流，支持条件分支、人工审批门、自动重试
- 长任务处理：超过 30 秒的任务需显示实时进度条和预计剩余时间；支持后台执行和通知提醒
- 任务队列管理：防止多个用户同时触发大量 AI 调用导致 API 限流
- 实时通信：WebSocket 推送流水线进度；企业防火墙阻断时降级为长轮询

### UX Design Requirements

无 UX Design 文档输入。所有 UX 相关需求已在 FR 和 NFR 中覆盖（如响应式设计、分屏审查界面、WCAG 2.1 AA 等）。

## Epic List

### Epic 1: 文档上传与智能解析
工程师可以将芯片手册、需求规格等上游文档上传至平台，平台自动解析并提取结构化功能需求、寄存器定义及安全关键参数。
**FRs covered:** FR1, FR2, FR3, FR4

### Epic 2: 方案设计与审查协作
工程师基于解析的结构化需求，在平台内生成符合 ASPICE Level 2 的设计文档，通过分屏界面逐节审查并记录结构化评审意见。
**FRs covered:** FR5, FR6, FR7

### Epic 3: 合规代码自动生成
平台基于已批准的设计文档，自动生成符合 MISRA C/C++ 规范、内嵌 Polarion 追溯 ID 的 C 语言模块代码，并根据声明的 ASIL 等级自动调整生成策略。
**FRs covered:** FR8, FR9, FR10, FR11

### Epic 4: 测试用例生成
平台基于需求和设计文档自动生成测试用例，系统覆盖边界条件、等价类划分和故障注入场景。
**FRs covered:** FR12, FR13

### Epic 5: 静态测试与代码质量分析
平台对生成代码执行 MISRA 合规检查、代码复杂度分析、代码规范与风格一致性扫描，并生成合规报告。
**FRs covered:** FR14, FR15, FR16

### Epic 6: 动态测试执行与验证
平台自动构建 Mock/Stub 环境并执行单元测试，验证接口一致性，监控资源使用，执行回归测试，并生成语句/分支/MC/DC 覆盖率报告。
**FRs covered:** FR17, FR18, FR19, FR20, FR21

### Epic 7: 网络安全合规审计
平台对生成代码执行安全漏洞审查，基于模块接口自动分析攻击面并按 CVSS 评级，验证 ISO 21434 基线安全需求的覆盖率。
**FRs covered:** FR22, FR23, FR24

### Epic 8: 发布管理与全链路追溯
平台将所有产物（设计文档、代码、测试用例、报告）打包为标准化交付物，内置完整的双向追溯链，并一键推送代码至 Git、文档/报告至 Polarion。
**FRs covered:** FR25, FR26, FR27

### Epic 9: 平台运维与治理
平台管理员可以配置 Polarion 和 AD/LDAP 集成、创建租户隔离空间、设定合规策略，并监控平台运行状态接收告警通知。
**FRs covered:** FR28, FR29, FR30, FR31

## Epic 1: 文档上传与智能解析

工程师可以将芯片手册、需求规格等上游文档上传至平台，平台自动解析并提取结构化功能需求、寄存器定义及安全关键参数。

### Story 1.1: 文档上传与分片传输

**As a** 嵌入式软件工程师,  
**I want** 上传芯片手册、需求规格等上游文档到 Modu 平台,  
**So that** 平台可以开始解析和处理我的输入文档。

**Acceptance Criteria:**

- **Given** 工程师在 Web 界面上传文档
- **When** 文档大小 ≤ 100MB 且格式为 PDF/Word/Excel/图片/TXT/PPT
- **Then** 前端使用分片上传机制完成上传
- **And** 系统返回文档解析任务 ID，工程师可通过该 ID 查询解析进度

### Story 1.2: 文档解析与结构化需求提取

**As a** 嵌入式软件工程师,  
**I want** 平台自动解析我上传的文档并提取结构化需求,  
**So that** 我可以查看和审查芯片的功能需求和寄存器定义。

**Acceptance Criteria:**

- **Given** 文档上传完成且解析任务已触发
- **When** 平台执行文档解析（Celery 异步任务）
- **Then** 对于标准格式 PDF/Word，解析成功率 ≥ 95%
- **And** 解析结果以结构化需求条目呈现，每条包含：需求 ID、需求描述、来源文档章节、ASIL 等级（如声明）
- **And** 解析结果在 Web 界面以可浏览的树形结构展示

### Story 1.3: 安全关键参数识别与可追溯注册

**As a** 嵌入式软件工程师,  
**I want** 平台自动识别文档中的安全关键参数并注册为独立可追溯条目,  
**So that** 时序、电压阈值、温度范围、看门狗周期等安全参数不会被遗漏。

**Acceptance Criteria:**

- **Given** 文档解析结果中存在安全关键参数（时序、电压阈值、温度范围、看门狗周期、超时时间等）
- **When** 平台执行安全关键参数识别
- **Then** 每个参数以 `SW-REQ-SAF-xxx` 编号独立标识，不嵌入功能描述段落
- **And** 每个安全关键参数条目包含：参数名、数值、单位、容差、来源文档页码/章节
- **And** 安全关键参数条目与普通功能需求条目在界面上分区展示

### Story 1.4: OCR 置信度评分与低置信度阻断

**As a** 嵌入式软件工程师,  
**I want** 平台对扫描件或图片格式文档的 OCR 结果输出置信度评分,  
**So that** 我可以对低置信度提取结果进行人工复核，避免错误数据流入下游代码生成。

**Acceptance Criteria:**

- **Given** 上传文档为扫描件或图片格式（JPG/PNG/TIFF/PDF 扫描件）
- **When** 平台执行 OCR 提取和数值字段识别
- **Then** 每个提取的数值字段附带置信度分数（0.0–1.0）
- **And** 置信度 < 0.95 的数值字段自动标记为"需人工复核"
- **And** 存在未复核的低置信度字段时，流水线自动阻塞，不允许进入方案设计阶段
- **And** 工程师在界面对低置信度字段签名确认后，阻塞解除

## Epic 2: 方案设计与审查协作

工程师基于解析的结构化需求，在平台内生成符合 ASPICE Level 2 的设计文档，通过分屏界面逐节审查并记录结构化评审意见。

### Story 2.1: 设计文档自动生成

**As a** 嵌入式软件工程师,  
**I want** 平台基于已解析的结构化需求自动生成设计文档,  
**So that** 我获得符合 ASPICE Level 2 规范的方案设计初稿，可直接导入 Polarion。

**Acceptance Criteria:**

## Epic 9: 平台运维与治理

平台管理员可以配置 Polarion 和 AD/LDAP 集成、创建租户隔离空间、设定合规策略，并监控平台运行状态接收告警通知。

### Story 9.1: Polarion ALM 集成配置

**As a** 平台管理员,  
**I want** 配置 Siemens Polarion ALM 的连接参数和导入映射规则,  
**So that** 平台可以将产物正确导入客户的 Polarion 实例。

**Acceptance Criteria:**

- **Given** 管理员进入平台管理后台的集成配置页面
- **When** 配置 Polarion 服务器地址、项目空间、Work Item 类型映射、自定义字段映射
- **Then** 配置界面支持可视化字段映射（Polarion 字段 ↔ 平台字段）
- **And** 配置完成后可一键验证连通性和权限，返回测试导入结果
- **And** 支持至少 3 种不同客户的 Polarion 配置适配（通过配置模板切换）

### Story 9.2: AD/LDAP 认证集成

**As a** 平台管理员,  
**I want** 配置与客户现有 AD/LDAP 认证系统的集成,  
**So that** 用户可以使用企业统一账号登录平台，无需单独维护用户体系。

**Acceptance Criteria:**

- **Given** 管理员进入认证配置界面
- **When** 配置 LDAP/LDAPS 服务器地址、基础 DN、用户/组过滤规则
- **Then** 支持标准 LDAP/LDAPS 协议，可配置服务器证书校验策略
- **And** 用户首次登录自动同步组织架构和角色权限（按 LDAP 组映射到平台角色）
- **And** 同时保留本地管理员账号作为备用认证方式，防止 LDAP 故障时无法登录

### Story 9.3: 租户隔离与合规策略配置

**As a** 平台管理员,  
**I want** 创建租户隔离空间并为不同团队配置独立的代码模板和合规策略,  
**So that** 不同团队的数据和配置完全隔离，且各自遵循自己的合规标准。

**Acceptance Criteria:**

- **Given** 管理员进入租户管理界面
- **When** 创建新租户空间
- **Then** 每个租户的数据、配置、产物完全隔离，租户管理员无法跨租户访问（数据库 RLS 强制执行）
- **And** 合规策略配置包括：默认 ASIL 等级、MISRA 规则集版本、代码模板版本、命名规范
- **And** 支持为每个租户独立上传和维护代码生成模板（JSONB 版本化管理，历史版本可追溯）

### Story 9.4: 平台监控与告警通知

**As a** 平台管理员,  
**I want** 监控平台运行状态并接收告警通知,  
**So that** 我可以及时发现和解决平台运维问题，保障服务稳定性。

**Acceptance Criteria:**

- **Given** 平台运行中
- **When** 监控指标触发告警阈值
- **Then** 监控指标包括：AI API 调用延迟、文档解析队列深度、存储容量使用率、系统错误率
- **And** 告警阈值可配置（按百分比或绝对值）
- **And** 告警通道支持邮件和企业消息推送（钉钉、企业微信、Teams）
- **And** 管理员可在监控仪表盘查看实时指标和历史趋势，支持按租户维度过滤
