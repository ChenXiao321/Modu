# Product Requirements Document - Modu

**Author:** Willi
**Date:** 2026-05-18

## Executive Summary

Modu 是一款面向汽车电子行业的 AI 驱动软件模块开发平台，部署于客户私有环境，通过 Web 界面提供端到端的智能开发流水线。平台将汽车电子软件开发的领域 know-how —— 包括 ASPICE 流程规范、ISO 26262 功能安全实践、ISO 21434 网络安全要求、MISRA 编码标准及 Siemens Polarion ALM 追溯机制 —— 沉淀为内置规则引擎，并借助第三方大模型 API 实现全流程自动化。

用户上传需求规格、架构设计、接口说明或芯片手册（支持 PDF / Word / Excel / 图片 / TXT / PPT 等格式）后，平台依次执行需求分析、方案设计、代码构建、测试用例生成、静态测试、动态测试执行及发布。每个阶段产出均内建双向追溯链接，可直接导入 Polarion 形成完整追溯矩阵。平台根据模块的实际 ASIL 等级（A/B/C/D）自动匹配合规流程、测试覆盖率目标及验证深度，确保从需求到代码到测试证据的全链路一致性。

MVP 阶段目标平台锁定为 Infineon AURIX TC38x + Tasking 6.3.1，用户需提供基础工程（Base Project）用于集成编译与测试。平台内置代码生成模板，约束 AI 输出代码的文件结构、命名风格、接口模式及编译器适配格式，确保生成代码可直接集成到用户工程。

### What Makes This Special

**合规内生于产出，而非事后补救。** 市面通用 AI 编程助手能生成代码，但缺乏对汽车电子合规流程的深度理解，无法输出满足车规要求的完整产物。Modu 将 ASPICE、ISO 26262、ISO 21434 的要求内建到每个活动步骤中，使工程师一键获得可追溯、可验证、可复现的工业化交付物，而非零散的代码片段。

**Know-how 沉淀与 democratization。** 平台将资深工程师的合规经验、文档规范、测试策略固化为自动化规则，使初级工程师在无培训情况下也能产出符合车规标准的成果，从根本上降低合规门槛和人力成本。

## Success Criteria

### User Success

- **开发效率**：目标将软件模块从需求到发布的平均周期缩短 40% 以上（预期值，需试点验证）
- **文档质量**：目标将设计文档首次评审通过率提升至 90% 以上（基线约 60%，预期值）
- **测试覆盖**：动态测试代码覆盖率达到对应 ASIL 等级的目标要求；静态测试零高危告警
- **合规达成**：目标通过第三方 ASPICE 及功能安全审核时，过程资产一次性通过率达到 95% 以上（预期值）
- **用户采用**：目标在试点项目中，80% 以上工程师可在无培训情况下完成首个模块开发（预期值）

### Business Success

*注：商业成功指标（客户获取、收入目标、NPS 等）由独立商业计划书定义，不纳入本 PRD 范围。*

### Technical Success

- **代码可构建性**：Modu 生成的模块代码在用户提供的 TC38x + Tasking 6.3.1 基础工程中可一次编译并通过链接（compile + link），生成可执行的目标文件。链接验收标准包括：符号解析完整、无未定义外部引用、与用户基础工程的 MCAL 版本兼容。
- **模板一致性**：所有生成代码符合平台内置代码生成模板的文件结构、命名风格、接口模式及编译器适配格式
- **追溯完整性**：所有产出物内置双向追溯链接，可完整导入 Siemens Polarion ALM 系统形成追溯矩阵
- **部署稳定性**：平台在私有化部署环境中稳定运行，不依赖外部互联网即可完成核心功能（第三方大模型 API 调用除外）
- **ASIL 适配**：平台能够根据输入需求中声明的 ASIL 等级（A/B/C/D）自动输出对应合规深度的产物

## Product Scope

### MVP - Minimum Viable Product

**核心功能：**
- 支持主流汽车电子软件模块（含外设驱动、通信协议栈、传感器抽象层等）的开发；平台为开放系统，通过 AI 解析用户上传的上游文档（需求、架构、接口、芯片手册等，支持 PDF/Word/Excel/图片/TXT/PPT）自动生成模块代码
- 覆盖完整流水线：需求分析 → 方案设计 → 代码生成 → 测试用例生成 → 静态测试 → 动态测试执行 → 发布
- 目标平台锁定为 Infineon AURIX TC38x + Tasking 6.3.1；用户需提供基础工程用于集成编译与测试
- 内建 ASPICE Level 2 过程要求及 ISO 26262 功能安全实践；根据模块实际 ASIL 等级自动匹配合规流程
- 平台内置代码生成模板与规范，约束 AI 输出格式
- 所有产出物内置双向追溯链接，对接 Siemens Polarion ALM 系统

**测试能力：**
- 静态测试：MISRA C/C++ 合规检查、代码复杂度分析、代码规范扫描
- 测试用例生成：基于需求与设计的边界条件/等价类用例、故障注入场景
- 动态测试执行：Mock/Stub 环境构建与单元测试执行、接口一致性验证、资源使用监控（内存/堆栈/CPU）、回归测试、覆盖率分析（语句/分支/MC/DC）
- 网络安全测试：依据 ISO 21434 的渗透测试、攻击面分析与安全需求验证

**平台能力：**
- 基于 Web 的统一操作界面，支持需求上传、流程跟踪、产物查看与评审
- 设计校验和人工确认机制，支持结构化评审记录（签名、时间戳、评审意见）

**明确排除（MVP 不做）：**
- 主芯片底层启动代码及操作系统移植（由用户提供基础工程覆盖）
- IDE 插件（VS Code / Eclipse）集成
- 与第三方工具链（Vector、EB tresos）的实时集成
- 硬件在环（HIL）系统级测试
- ISO 26262 工具认证（TCL 评估）流程
- ASIL-D 全套认证证据包的自动生成（平台支持按 ASIL-D 标准开发，证据包后续迭代）

### Growth Features (Post-MVP)

- IDE 插件集成（VS Code / Eclipse）
- 与第三方工具链（Vector、EB tresos）的实时集成
- 扩展目标平台支持（beyond TC38x，如 NXP S32K、Renesas RH850 等）
- 本地部署大模型（替代第三方 API，实现完全离线）
- 更多 ALM 系统集成（DOORS、Codebeamer 等）

### Vision (Future)

- 成为汽车电子软件模块开发领域的标杆工具
- 扩展至更广泛的中间件及复杂协议栈开发
- 覆盖 ASIL-D 等高等级功能安全场景（含全套认证证据包自动生成）
- 探索辅助生成功能安全分析（FMEA/FTA）的能力
- 成为汽车软件工程领域的"智能副驾驶"
- 与芯片厂商合作，反向提供 SDK 生成与验证服务，形成 B2B2B 生态闭环

## User Journeys

### Journey 1: 萌新工程师 — 从零到合规的首个模块

**人物**：小李，入职半年的嵌入式软件工程师，第一次独立负责 TLF35584 电源管理芯片的驱动开发。

**Opening Scene**：小李拿到芯片手册和需求规格书，面对 200 多页的全英文文档和严格的 ASPICE 流程要求，感到无从下手。他知道需要产出设计文档、代码、测试用例，但不知道从何开始，更担心文档评审被退回。

**Rising Action**：
1. 小李登录 Modu 平台，在向导式界面上传了芯片手册 PDF 和需求规格 Word 文档
2. 平台自动解析文档，提取并结构化出功能需求和寄存器定义
3. AI 基于内置模板生成方案设计文档，小李在 Web 界面上逐节审查，对 SPI 初始化时序部分做了人工修正
4. 平台自动生成符合 MISRA 规范的 C 代码，小李看到代码中已内嵌 Polarion 追溯 ID，不需要手动补链接
5. 测试用例自动生成，包括边界条件和故障注入场景，小李惊讶地发现平台连他没想到的电源过压场景都覆盖了

**Climax**：小李点击"执行全流程"，平台在 30 分钟内完成了静态测试（零高危告警）、动态测试（覆盖率 92%，满足 ASIL-B 要求）、并打包了所有交付物。他第一次在没有资深工程师手把手指导的情况下，产出了可以直接提交评审的完整模块。

**Resolution**：设计文档首次评审通过，项目经理惊讶于产出的完整性。小李从"需要人带"变成了"能独立交付"，他对汽车电子开发的恐惧感转化为信心。

**情感曲线**：😰 迷茫 → 😐 试探 → 😲 惊喜 → 💪 自信

### Journey 2: 资深工程师 — 从重复劳动中解放

**人物**：老张，十年经验的资深嵌入式工程师，负责车身电子模块的架构设计，厌倦了 endlessly 写评审意见和补文档。

**Opening Scene**：老张的团队新来了 3 个应届生，他花了 40% 的时间在帮他们改文档、补追溯链、解释 MISRA 规则。他内心清楚，这些重复性工作正在吞噬他本应花在系统架构上的时间。

**Rising Action**：
1. 老张在 Modu 上配置了一套团队代码模板（文件头、命名规范、错误处理模式），设定了 ASIL-B 的默认合规级别
2. 他将一个复杂的 CAN 通信协议需求丢给平台，自己同时处理另一个架构难题
3. 30 分钟后，平台生成了完整的方案设计、代码和测试用例。老张快速审查，只调整了 2 处接口定义，其余全部符合团队规范
4. 他让应届生用 Modu 完成 3 个外设驱动的开发，自己只需在设计校验节点做最终把关

**Climax**：季度评审时，团队交付了 12 个模块（以往平均 6 个），所有模块一次性通过 ASPICE 审核。老张终于有时间推进他构思已久的中间件抽象层重构。

**Resolution**：老张从"文档警察"变回了"架构师"。他发现 Modu 不是替代他，而是把他从重复劳动中解放出来，让他专注于真正创造价值的工作。

**情感曲线**：😤 烦躁 → 🤔 怀疑 → 😮 意外 → 😌 解脱 → 🚀 投入

### Journey 3: 质量审核员 — 从"找茬"到"验证"

**人物**：王工，ASPICE L3 评估师兼软件质量负责人，每月要审核数十份设计文档和测试报告，最头疼的是追溯链断裂和评审记录缺失。

**Opening Scene**：王工打开一个传统项目的审核包，发现需求条目 SW-REQ-047 在设计文档中被引用了，但在代码中没有对应的实现追溯；测试用例 TC-128 覆盖了需求，但测试执行记录缺失；评审会议开了，但没有人签名留档。他必须逐条写不符合项报告（NCR），项目因此延期两周。

**Rising Action**：
1. 王工登录 Modu 平台的"质量视图"，看到所有模块的开发流程状态一目了然：需求分析 → 方案设计 → 代码构建 → 测试 → 发布，每个节点的完成状态和人工确认记录清晰可见
2. 他点击"追溯矩阵审查"，平台自动展示了从需求到设计到代码到测试的全链路双向追溯图。他随机抽取了 10 个需求条目，发现每一个都有完整的下游实现和测试覆盖，Polarion 中的链接状态实时同步
3. 他检查评审记录，发现每个设计校验节点都有完整的签名、时间戳和评审意见，格式符合 ASPICE 要求，无法篡改
4. 他抽查静态测试报告，MISRA 合规检查零高危告警，圈复杂度分析显示所有函数均在阈值内
5. 他核对 ASIL-B 模块的测试覆盖率，语句覆盖 95%、分支覆盖 88%，满足该等级要求

**Climax**：王工在 2 小时内完成了以往需要 2 天的审核工作，且没有发现一个追溯断裂或记录缺失。他出具审核报告时，第一次没有写 NCR，只写了 3 条改进建议。

**Resolution**：王工从"挑错的人"变成了"流程优化的顾问"。他开始主动研究如何利用 Modu 的审计数据优化团队的整体开发流程，而不是被动地等项目出问题后救火。

**情感曲线**：😩 疲惫 → 😤 不满 → 🧐 审视 → 😲 惊讶 → 🤝 合作 → 💡 前瞻

**此旅程揭示的关键能力需求：**
- **质量仪表盘**：流程状态可视化、模块健康度评分
- **追溯矩阵审查工具**：双向追溯图、链接完整性自动校验
- **评审记录审计**：结构化评审记录（签名、时间戳、意见）不可篡改存储
- **合规报告自动生成**：按 ASPICE/ISO 26262 要求格式化输出审核证据
- **ASIL 等级验证**：自动匹配并显示当前模块的合规深度是否满足声明等级

**Rising Action**：

**情感曲线**：🤔 审慎 → 🔧 动手 → ✅ 验证 → 😌 安心 → 🔮 前瞻

### Journey 5: 网络安全工程师 — ISO 21434 合规验证

**人物**：陈工，网络安全部门的 TARA（Threat Analysis and Risk Assessment）分析师，负责审核汽车电子模块的网络安全合规性，依据 ISO 21434 标准评估每个模块的攻击面和安全需求覆盖率。

**Opening Scene**：陈工收到一个由 Modu 生成的 BMS 通信模块交付包。按照公司流程，他需要在模块发布前完成网络安全审计，包括攻击面分析、安全需求追溯和潜在漏洞审查。以往他最头疼的是：安全需求散落在不同文档中，攻击面分析依赖人工逐行审查代码，耗时且容易遗漏。

**Rising Action**：
1. 陈工登录 Modu 的"安全视图"，看到该模块已自动生成的 ISO 21434 合规报告：攻击面清单（SPI 接口、诊断服务入口、CAN 报文接口）、安全需求追溯矩阵、以及代码级安全审查结果
2. 他审查攻击面分析报告，平台基于模块接口设计自动识别了所有外部通信入口，并按 CVSS 评分排序了风险等级。陈工发现平台遗漏了一个调试接口的攻击场景，在线补充后，平台自动更新了追溯矩阵
3. 他检查安全代码审查报告：平台静态扫描识别了所有潜在的缓冲区溢出、整数溢出和未初始化指针使用，并提供了修复建议。陈工确认所有高危项已清零
4. 他验证安全需求覆盖率：平台自动将 ISO 21434 要求的 28 项基线安全需求映射到模块设计和测试用例，陈工逐项确认，发现覆盖率达到 100%
5. 他导出网络安全审计证据包，包含攻击面分析、安全需求验证记录、代码审查报告和异常处理策略，格式符合公司内部网络安全审核模板

**Climax**：陈工在 1 小时内完成了以往需要 2 天的网络安全审计工作。更重要的是，由于所有分析基于设计文档和代码自动执行，而非人工主观判断，审核结果的可重复性和可追溯性大幅提升。

**Resolution**：陈工将 Modu 的网络安全审计证据包直接提交给外部网络安全认证机构，一次性通过审查。他开始推动将 Modu 的安全视图作为公司内部所有汽车电子模块发布的强制门禁。

**情感曲线**：😐 例行公事 → 🧐 审视 → 😮 效率提升 → 💡 价值认可 → 🚀 流程变革

**此旅程揭示的关键能力需求：**
- **安全视图仪表盘**：自动聚合模块的网络安全分析结果，按 ISO 21434 框架组织
- **攻击面自动分析**：基于模块接口设计自动识别外部入口并评估风险等级
- **安全代码审查**：静态分析聚焦安全漏洞（缓冲区溢出、整数溢出、指针安全）
- **安全需求追溯矩阵**：将 ISO 21434 基线安全需求自动映射到设计和测试用例
- **网络安全审计证据包**：一键导出符合认证机构格式的完整证据包

## Domain-Specific Requirements

### Compliance & Regulatory

- **ASPICE Level 2**：过程能力要求，涵盖需求管理、设计、实现、测试、配置管理
- **ISO 26262 功能安全**：根据模块 ASIL 等级（A/B/C/D）匹配对应的开发流程、测试覆盖率和验证深度
- **ISO 21434 网络安全**：动态测试阶段执行渗透测试、攻击面分析和安全需求验证
- **MISRA C/C++**：代码规范合规检查，静态测试零高危告警
- **TCL（Tool Confidence Level）**：MVP 排除，后续迭代启动 ISO 26262 工具认证评估

### Technical Constraints

- **目标平台锁定**：Infineon AURIX TC38x + Tasking 6.3.1 + **AUTOSAR Classic**
- **模块类型**：**CDD（Complex Device Driver）** — 可直接访问微控制器硬件，不受标准 AUTOSAR 接口严格约束
- **私有化部署**：数据不出内网，适配客户内部网络环境和安全策略
- **AI 模型调用**：第三方大模型 API 需经过企业审计网关，所有请求留痕
- **代码可编译性**：生成代码必须能在用户提供的 AUTOSAR Base Project 中一次编译通过

### Integration Requirements

- **Siemens Polarion ALM**：文档/测试用例/测试报告提交至 Polarion，形成 Work Item 和 LiveDoc 结构；双向追溯矩阵
- **Git**：代码产物（源文件、头文件）提交至 Git 仓库；支持代码评审（PR/MR）流程；变更历史可追溯
- **AD/LDAP**：与客户现有用户管理体系集成
- **用户基础工程（Base Project）**：Modu 生成 CDD 代码集成到客户 AUTOSAR 工程，不生成启动代码和 OS 移植

### Risk Mitigations

- **数据安全**：芯片手册常涉及 NDA，平台需确保文档解析和处理过程中数据不泄露
- **AI 幻觉风险**：AI 生成的代码和文档可能存在错误，通过设计校验节点和人工确认机制把关
- **合规偏差风险**：不同客户对 ASPICE/ISO 26262 的理解可能不同，平台模板需支持一定定制化
- **供应商锁定**：第三方大模型 API 存在供应商锁定风险，架构需支持可插拔切换为本地模型
- **版本控制一致性**：Git commit 与 Polarion Work Item 之间的追溯关联需保持一致

## Innovation & Novel Patterns

### Detected Innovation Areas

**1. 合规原生型 AI 代码生成（Compliance-Native AI Code Generation）**
传统 AI 编程助手（GitHub Copilot、ChatGPT）聚焦于"生成能跑的代码"，而 Modu 的创新在于"生成**能通过审核**的代码"。平台将 MISRA 规则、ASPICE 流程要求、ISO 26262 安全实践编码为 AI 的约束条件，使生成的每一行代码、每一份文档从诞生之初就携带合规基因。这不是在代码生成后叠加检查，而是在生成过程中内建规则。

**2. 端到端追溯自动化（End-to-End Traceability Automation）**
汽车电子行业长期面临追溯链维护的人工负担。Modu 的创新在于：从需求分析阶段开始，每个产物（需求、设计、代码、测试用例、测试报告）自动生成并维护双向追溯链接，直接同步到 Polarion ALM。工程师不需要手动创建链接、维护矩阵，平台在流水线执行过程中自动完成。

**3. ASIL 感知开发（ASIL-Aware Development）**
平台根据输入需求中声明的 ASIL 等级，自动调整整个开发流程的严格程度 —— 从测试覆盖率目标、文档深度、故障注入场景到代码审查清单。同一平台可以服务 ASIL-A 的车身舒适模块和 ASIL-D 的制动安全模块，而不需要两套独立流程。

**4. 领域 Know-how 的 AI 化沉淀（Domain Know-How AI Codification）**
将汽车电子领域资深工程师的隐性经验（如何写一份能通过评审的设计文档、如何设计满足 MC/DC 的测试用例、如何组织 Polarion Work Item）转化为可复用的平台规则和代码模板，实现经验的规模化复制。

### Market Context & Competitive Landscape

当前市场存在两类工具：
- **芯片厂商配置工具**（如 STM32CubeMX）：仅覆盖单点（代码生成），局限于主芯片，无合规能力
- **通用 AI 编程助手**（如 GitHub Copilot）：生成代码片段，但不理解 ASPICE、ISO 26262、Polarion 追溯

Modu 填补了两者之间的空白：**既具备 AI 的生成能力，又具备汽车电子合规的专业深度**。这是一个垂直领域的"AI 原生"工具，而非通用工具的行业适配版。

### Validation Approach

- **试点项目验证**：在 1-2 个真实模块上对比 Modu 产出与传统人工产出的审核结果
- **第三方审核**：邀请 ASPICE 评估师对 Modu 生成的过程资产进行独立审核
- **用户采用率追踪**：统计试点工程师在无培训情况下的首次完成率

### Risk Mitigation

- **AI 幻觉风险**：通过设计校验节点和强制人工确认机制兜底
- **合规标准更新风险**：平台模板需支持版本化更新（如 MISRA 2023 → 2025）
- **客户定制化需求**：不同 OEM 对 ASPICE 理解有差异，模板需支持参数化配置

## Web Application Specific Requirements

### Project-Type Overview

Modu 是一款 B2B 企业级 Web 应用平台，私有化部署于客户内网，面向汽车电子工程师和质量审核员。与面向消费者的 Web 应用不同，Modu 不需要 SEO、社交媒体集成或移动端优先设计，而是聚焦于**复杂文档处理、长时运行任务、企业级安全与合规**。

### Technical Architecture Considerations

**前端交互能力**
- 工程师可在平台内持续执行开发任务而不因页面切换丢失工作流上下文；关键交互场景包括：文档上传 → 侧边栏进度跟踪 → 分屏审查（左侧原文档、右侧 AI 生成内容）→ 在线编辑与确认

**浏览器支持矩阵：**

| 浏览器 | 最低版本 | 支持级别 |
|--------|---------|---------|
| Google Chrome | 最新 2 个主版本 | 完全支持 |
| Microsoft Edge | 最新 2 个主版本 | 完全支持 |
| Mozilla Firefox | 最新 2 个主版本 | 完全支持 |
| Safari | 最新 2 个主版本 | 最佳 effort（非主要目标） |
| Internet Explorer | 不支持 | 明确排除 |

*注：企业环境以 Chrome/Edge 为主，Safari 支持可作为后续优化。*

**响应式设计：**
- 主要面向桌面端（1920×1080 及以上分辨率），支持工程师使用大屏幕进行分屏审查
- 最小支持分辨率：1366×768（笔记本用户）
- 不做移动端优先适配（工程师不会在手机上开发驱动模块）

### Performance Targets

| 场景 | 目标响应时间 | 说明 |
|------|-------------|------|
| 页面首次加载 | ≤ 3 秒 | 内网环境，带宽充足 |
| 文档上传（< 50MB） | ≤ 10 秒 | 含 PDF/Word 解析启动 |
| AI 需求分析（单文档） | ≤ 60 秒 | 取决于文档复杂度 |
| 代码生成（单模块） | ≤ 90 秒 | 含方案设计 + 代码 + 测试用例 |
| 静态测试执行 | ≤ 30 秒 | MISRA 扫描 + 复杂度分析 |
| 动态测试执行 | ≤ 5 分钟 | 含编译 + Mock 构建 + 单元测试运行 |
| 全流程执行 | ≤ 10 分钟 | 从需求到发布的完整流水线 |

**长任务处理：**
- 超过 30 秒的任务需显示实时进度条和预计剩余时间
- 支持后台执行，用户可离开页面并在完成后通过通知提醒返回
- 任务队列管理：防止多个用户同时触发大量 AI 调用导致 API 限流

### Real-Time Requirements

- **非实时协作**：汽车电子模块开发通常为单人负责，不需要 Google Docs 式的多人实时协同编辑
- **实时通知**：平台向已订阅的客户端推送设计校验节点到达、审核请求、流水线执行完成等事件的实时通知，确保用户在不刷新页面的情况下获知状态变更
- **状态同步**：模块开发流程状态（需求分析中/方案设计待审查/测试中）需实时刷新，避免多用户查看时状态不一致

### Accessibility Level

- **目标等级**：WCAG 2.1 AA（满足企业合规基础要求）
- **关键要求**：键盘导航支持、高对比度模式、屏幕阅读器友好（表单标签、ARIA 属性）
- **非核心优先级**：由于主要用户为视力正常的工程师，无障碍支持达到"可用"级别即可，不需要极致优化

### Implementation Considerations

**文件处理：**
- 前端需支持大文件上传（PDF/Word 可能达 100MB+），使用分片上传或流式上传
- 图片格式文档（扫描件）需前端预览 + 后端 OCR 结合处理
- 文档解析结果需在浏览器端缓存，避免重复上传后的重复解析

**安全要求：**
- 所有通信通过 HTTPS/TLS（即使在内网）
- 前端不直接存储敏感文档内容，仅显示处理后的结构化数据
- AI API 调用参数需脱敏（如芯片型号、客户项目名称可在前端隐藏）

**离线 resilience：**
- 流水线执行过程中若网络中断，需支持断点续传或任务重试
- 表单输入（如人工评审意见）需本地自动保存，防止意外刷新丢失

## Functional Requirements

以下需求按用户角色与能力域组织，采用 `[执行者] 可以 [能力]` 格式，每条附带验收标准（Acceptance Criteria）。

### REQ-1 文档输入与需求分析

**FR-REQ-001** 工程师可以上传上游输入文档（需求规格、架构设计、接口说明、芯片手册等），支持 PDF、Word、Excel、图片、TXT、PPT 格式，单文件最大 100MB。
- **AC1:** 前端支持分片上传，100MB 文件在带宽 ≥ 100Mbps 内网环境下可在 30 秒内完成上传。
- **AC2:** 上传完成后，平台返回文档解析任务 ID，工程师可通过该 ID 查询解析进度。

**FR-REQ-002** 平台可以自动解析上传文档并提取结构化功能需求与寄存器定义。
- **AC1:** 对于标准格式 PDF/Word，解析成功率 ≥ 95%。
- **AC2:** 解析结果以结构化需求条目形式呈现，每条包含：需求 ID、需求描述、来源文档章节、ASIL 等级（如声明）。

**FR-REQ-003** 平台可以识别并单独标注安全关键参数（时序、电压阈值、温度范围、看门狗周期、超时时间等），将其注册为独立可追溯需求条目。
- **AC1:** 安全关键参数在解析结果中以 `SW-REQ-SAF-xxx` 编号独立标识，不嵌入功能描述段落。
- **AC2:** 每个安全关键参数条目包含：参数名、数值、单位、容差、来源文档页码/章节。

**FR-REQ-004** 平台可以对扫描件或图片格式文档的 OCR 提取结果输出置信度评分。
- **AC1:** 每个提取的数值字段附带置信度分数（0.0–1.0）。
- **AC2:** 置信度 < 0.95 的数值字段自动标记为"需人工复核"，阻断后续代码生成直至工程师签名确认。

### REQ-2 方案设计

**FR-REQ-005** 平台可以基于解析后的结构化需求生成符合 ASPICE Level 2 要求的设计文档。
- **AC1:** 设计文档包含以下章节：概述、引用文档、系统架构、接口定义、动态行为、资源消耗估算、错误处理策略、测试策略。
- **AC2:** 设计文档中每个章节均内嵌 Polarion 追溯 ID，可直接导入 Polarion LiveDoc。

**FR-REQ-006** 工程师可以在 Web 界面逐节审查设计文档，对任意章节进行在线修正或添加评审意见。
- **AC1:** 审查界面支持分屏显示（左侧原始文档、右侧 AI 生成设计）。
- **AC2:** 工程师的修改和评审意见以修订记录形式保存，包含作者、时间戳和修改前后差异。

**FR-REQ-007** 平台可以在每个设计校验节点记录结构化评审记录，包含签名、时间戳和评审意见。
- **AC1:** 评审记录不可篡改，存储于平台审计日志中，保留周期 ≥ 7 年。
- **AC2:** 未通过设计校验节点的模块，流水线自动阻塞，不允许进入代码生成阶段。

### REQ-3 代码构建

**FR-REQ-008** 平台可以基于已批准的设计文档生成符合 MISRA C/C++ 规范的 C 语言模块代码。
- **AC1:** 生成代码通过 MISRA C:2012 静态扫描，零高危告警。
- **AC2:** 代码复杂度：每个函数圈复杂度 ≤ 15。

**FR-REQ-009** 生成代码必须内嵌 Polarion 需求追溯 ID，实现需求到代码的双向追溯。
- **AC1:** 每个函数头注释中包含其对应的 Polarion 需求 Work Item ID。
- **AC2:** 代码文件头包含模块级追溯 ID 和代码生成模板版本号。

**FR-REQ-010** 生成代码应符合平台内置代码生成模板的文件结构、命名风格、接口模式及编译器适配格式。
- **AC1:** 代码文件结构遵循 AUTOSAR CDD 规范（含 `Modu_<ModuleName>.c` / `.h`、配置头文件、回调接口文件）。
- **AC2:** 命名风格遵循客户团队配置的模板（默认 camelCase / snake_case 可配置）。

**FR-REQ-011** 平台可以根据模块声明的 ASIL 等级（A/B/C/D）自动调整代码生成策略和验证深度。
- **AC1:** ASIL-A 模块：语句覆盖 ≥ 80%，分支覆盖 ≥ 70%。
- **AC2:** ASIL-B 模块：语句覆盖 ≥ 90%，分支覆盖 ≥ 80%，MC/DC 覆盖 ≥ 50%。
- **AC3:** ASIL-C/D 模块：语句覆盖 ≥ 95%，分支覆盖 ≥ 90%，MC/DC 覆盖 ≥ 70%。

### REQ-4 测试用例生成

**FR-REQ-012** 平台可以基于需求和设计文档自动生成测试用例。
- **AC1:** 每个功能需求至少生成 1 个正向测试用例和 1 个异常测试用例。
- **AC2:** 测试用例以标准化格式输出（含 Test Case ID、前置条件、执行步骤、期望结果、通过标准）。

**FR-REQ-013** 测试用例必须覆盖边界条件、等价类划分和故障注入场景。
- **AC1:** 边界条件覆盖：所有数值型参数的最小值、最大值、典型值、边界外值。
- **AC2:** 故障注入场景覆盖：通信超时、电源异常、看门狗复位、非法寄存器访问。

### REQ-5 静态测试

**FR-REQ-014** 平台可以执行 MISRA C/C++ 合规检查并生成合规报告。
- **AC1:** 静态扫描覆盖 MISRA C:2012 强制规则（Mandatory）和必要规则（Required）。
- **AC2:** 报告区分：高危（High）、中危（Medium）、低危（Low）三级告警。

**FR-REQ-015** 平台可以执行代码复杂度和圈复杂度分析。
- **AC1:** 输出每个函数的圈复杂度、嵌套深度、可维护性指数。
- **AC2:** 圈复杂度 > 15 的函数自动标记为重构建议项。

**FR-REQ-016** 平台可以执行代码规范与风格一致性扫描。
- **AC1:** 扫描项包括：命名规范、缩进风格、注释格式、文件头模板一致性。
- **AC2:** 风格偏差以警告形式呈现，不阻塞流水线（除非客户模板配置为强制）。

### REQ-6 动态测试执行

**FR-REQ-017** 平台可以自动构建 Mock/Stub 环境并执行单元测试。
- **AC1:** Mock/Stub 自动生成，覆盖模块所有外部依赖接口（MCAL、其他 CDD、OS 服务）。
- **AC2:** 单元测试在模拟 TC38x 目标环境的编译器配置下执行（Tasking 6.3.1，--iso=99）。

**FR-REQ-018** 平台可以执行接口/API 一致性验证。
- **AC1:** 验证生成代码的公共接口（函数签名、参数类型、返回值）与设计文档定义一致。
- **AC2:** 接口变更导致不一致时，自动标记并阻断发布。

**FR-REQ-019** 平台可以监控并记录动态测试期间的资源使用（内存、堆栈、CPU 占用）。
- **AC1:** 输出测试用例执行期间的堆栈最大深度、RAM 使用量、CPU 周期数（基于模拟器）。
- **AC2:** 资源使用超出客户定义阈值时自动告警。

**FR-REQ-020** 平台可以执行回归测试，在模块迭代时自动重跑全量历史用例。
- **AC1:** 回归测试触发条件：代码生成模板更新、需求变更、设计变更。
- **AC2:** 回归测试报告标注新增失败用例与历史通过/失败趋势。

**FR-REQ-021** 平台可以生成代码覆盖率报告（语句覆盖、分支覆盖、MC/DC）。
- **AC1:** 覆盖率报告按函数和模块两级汇总。
- **AC2:** 覆盖率数据自动关联到 Polarion 测试用例 Work Item，形成测试→需求的追溯。

### REQ-7 网络安全测试

**FR-REQ-022** 平台可以执行安全代码审查，检测生成代码中的安全漏洞。
- **AC1:** 审查覆盖：缓冲区溢出、整数溢出、不安全指针使用、格式化字符串漏洞。
- **AC2:** 安全审查高危项清零方可进入发布阶段。

**FR-REQ-023** 平台可以基于模块接口设计执行攻击面分析。
- **AC1:** 自动识别所有外部通信入口（SPI、CAN、诊断服务、调试接口）。
- **AC2:** 按 CVSS v3.1 评分标准对每个攻击面进行风险评级（Critical / High / Medium / Low）。

**FR-REQ-024** 平台可以验证 ISO 21434 基线安全需求的覆盖率。
- **AC1:** 将 ISO 21434 要求的基线安全需求映射到模块设计决策和测试用例。
- **AC2:** 输出安全需求覆盖率报告，未覆盖需求以阻塞项形式呈现。

### REQ-8 发布与追溯

**FR-REQ-025** 平台可以将所有产出物（设计文档、源代码、测试用例、测试报告、评审记录、追溯矩阵）打包为符合组织标准的交付物。
- **AC1:** 交付物包包含标准化目录结构和清单文件（Manifest）。
- **AC2:** 交付物包可直接导入客户配置管理系统或 Polarion ALM。

**FR-REQ-026** 所有产出物必须内置双向追溯链接，实现需求↔设计↔代码↔测试的完整追溯链。
- **AC1:** 每个产物中的追溯 ID 可在 Polarion 中解析为有效链接。
- **AC2:** 追溯矩阵完整性自动校验：任一需求条目若缺少下游设计、代码或测试链接，自动标记为阻断项。

**FR-REQ-027** 平台可以将代码产物（源文件、头文件）提交至 Git 仓库，并将文档/测试用例/报告提交至 Siemens Polarion ALM 系统。
- **AC1:** Git 提交附带 Polarion Work Item ID 的提交信息，实现代码变更到需求的双向追溯。
- **AC2:** Polarion 导入支持客户自定义的 Work Item 类型和字段映射（通过配置界面适配）。

### REQ-9 平台管理

**FR-REQ-028** 平台管理员可以配置 Siemens Polarion ALM 的连接参数和导入映射规则。
- **AC1:** 支持配置 Polarion 服务器地址、项目空间、Work Item 类型映射、自定义字段映射。
- **AC2:** 连接测试功能：配置完成后可一键验证连通性和权限。

**FR-REQ-029** 平台管理员可以配置与客户现有 AD/LDAP 认证系统的集成。
- **AC1:** 支持标准 LDAP/LDAPS 协议，可配置服务器地址、基础 DN、用户/组过滤规则。
- **AC2:** 用户首次登录自动同步组织架构和角色权限。

**FR-REQ-030** 平台管理员可以创建租户隔离空间，为不同团队配置独立的代码模板和合规策略。
- **AC1:** 每个租户的数据、配置、产物完全隔离，租户管理员无法跨租户访问。
- **AC2:** 合规策略配置包括：默认 ASIL 等级、MISRA 规则集版本、代码模板版本。

**FR-REQ-031** 平台管理员可以监控平台运行状态并接收告警通知。
- **AC1:** 监控指标包括：AI API 调用延迟、文档解析队列深度、存储容量使用率、系统错误率。
- **AC2:** 告警阈值可配置，告警通道支持邮件和企业消息推送（如钉钉、企业微信、Teams）。

## Non-Functional Requirements

以下质量属性按 `准则 + 指标 + 测量方法 + 上下文` 模板规范化。

### PERF 性能

**NFR-PERF-001** 系统应保证页面首次加载时间 ≤ 3 秒（95th percentile），测量方法为首屏内容渲染完成（FCP），上下文为内网环境（带宽 ≥ 100Mbps，延迟 ≤ 5ms）。

**NFR-PERF-002** 系统应保证文档上传（< 50MB）完成时间 ≤ 10 秒，测量方法为客户机发送完最后一个字节到服务器返回确认的时间，上下文为内网环境、PDF/Word 格式。

**NFR-PERF-003** 系统应保证 AI 需求分析（单文档，≤ 50 页）完成时间 ≤ 60 秒，测量方法为从用户点击"开始分析"到解析结果呈现的时间，上下文为文档以标准排版格式存储、AI API 正常响应。

**NFR-PERF-004** 系统应保证代码生成（单模块，含方案设计 + 代码 + 测试用例）完成时间 ≤ 90 秒，测量方法为从用户确认设计到所有产物生成完毕的时间，上下文为 ASIL-B 等级模块、标准 CDD 复杂度。

**NFR-PERF-005** 系统应保证静态测试执行完成时间 ≤ 30 秒，测量方法为从代码提交静态扫描到报告生成的时间，上下文为单模块代码量 ≤ 5000 行。

**NFR-PERF-006** 系统应保证动态测试执行（含编译 + Mock 构建 + 单元测试运行）完成时间 ≤ 5 分钟，测量方法为从测试触发到覆盖率报告生成的时间，上下文为 Tasking 6.3.1 编译器、TC38x 模拟目标环境。

**NFR-PERF-007** 系统应保证全流程执行（从需求上传到发布打包）完成时间 ≤ 10 分钟，测量方法为平台自动执行阶段的累计时间（不含人工审查等待时间），上下文为标准复杂度 CDD 模块、无队列阻塞。

### REL 可靠性

**NFR-REL-001** 系统在私有化部署环境中的可用性应 ≥ 99.5%，测量方法为月度正常运行时间 / 总时间，上下文为单实例部署、计划内维护窗口除外。

**NFR-REL-002** 系统应在流水线执行过程中遭遇网络中断时支持任务重试或断点续传，测量方法为模拟网络中断 30 秒后恢复，验证任务状态一致性和产物完整性，上下文为 AI API 调用阶段或文档解析阶段。

**NFR-REL-003** 系统应保证表单输入（如人工评审意见）在意外刷新或浏览器崩溃后不丢失，测量方法为输入后 5 秒内强制刷新页面，验证数据恢复完整性，上下文为所有包含文本输入的 Web 表单。

### SEC 安全性

**NFR-SEC-001** 系统应保证所有客户端与服务端通信通过 HTTPS/TLS 1.2 或更高版本加密，测量方法为网络抓包验证无明文传输，上下文为内网及跨网段访问场景。

**NFR-SEC-002** 系统应保证敏感文档原文不在前端浏览器持久存储（LocalStorage / IndexedDB），仅缓存处理后结构化数据，测量方法为审查前端存储内容，确认不包含原始 PDF/Word 二进制片段，上下文为所有支持的浏览器。

**NFR-SEC-003** 系统应保证 AI API 调用参数中不包含客户敏感信息（芯片型号、客户项目名称、内部架构细节），测量方法为审计网关日志，确认传出请求经过脱敏处理，上下文为所有第三方大模型 API 调用。

**NFR-SEC-004** 系统应记录所有 AI API 调用的完整审计日志，包含用户标识、时间戳、请求摘要、响应状态、模型版本，测量方法为审计日志完整性校验，保留周期 ≥ 2 年，上下文为私有化部署环境中的审计网关。

### MAINT 可维护性

**NFR-MAINT-001** 系统应支持代码生成模板的版本化管理，允许管理员升级模板版本而不影响历史模块产物，测量方法为验证同一模块使用模板 v1 和 v2 生成产物可追溯且互不覆盖，上下文为模板更新发布流程。

**NFR-MAINT-002** 系统应支持平台平滑升级，保证用户数据和配置无损迁移，测量方法为升级前后数据库 schema 兼容性验证和数据完整性校验，上下文为主版本号变更（如 1.x → 2.x）。

### USAB 可用性

**NFR-USAB-001** 系统应支持 Google Chrome、Microsoft Edge、Mozilla Firefox 的最新 2 个主版本完全兼容，测量方法为自动化 UI 测试覆盖核心用户旅程，上下文为桌面端浏览器。

**NFR-USAB-002** 系统应保证在 1920×1080 分辨率下完全展示所有功能界面，在 1366×768 分辨率下核心功能可用，测量方法为视觉回归测试，上下文为工程师常用桌面显示器和笔记本电脑。

**NFR-USAB-003** 系统应满足 WCAG 2.1 AA 级无障碍要求，测量方法为自动化无障碍扫描（如 axe-core）零 Critical 级别违规，上下文为所有公共页面和表单。

### SCAL 可扩展性

**NFR-SCAL-001** 系统架构应支持将第三方大模型 API 切换为本地部署模型，切换过程不改变业务层接口，测量方法为验证 API 适配层接口稳定性（至少支持 2 种不同模型后端），上下文为未来本地 GPU 集群部署。

**NFR-SCAL-002** Polarion 集成层应支持客户自定义 Work Item 类型、自定义字段和自定义链接角色，测量方法为配置界面验证至少 3 种不同客户的 Polarion 配置适配，上下文为不同 OEM/Tier-1 客户的 Polarion 实例。
